# bank-microservice-threat-model
## Анализ архитектуры, модель угроз и процесс управления уязвимостями для микросервиса перевода средств

**Объект анализа:** банковский микросервис (перевод средств между счетами + история транзакций)
**Стек:** FastAPI (Backend API) · PostgreSQL · Redis

## 1. Архитектура приложения (кратко)

| Компонент | Технология | Назначение |
|---|---|---|
| Backend API | FastAPI (Python, async) | `POST /transfer` — перевод между счетами; `GET /transactions` — история транзакций |
| База данных | PostgreSQL (`asyncpg`) | Таблицы `accounts` (баланс), `transactions` (история) |
| Кэш | Redis | Кэширование результата `GET /transactions` по ключу `tx:{user_id}:{limit}:{search}` |
| Идентификация | HTTP-заголовок `X-User-Id` | **Учебно упрощённая** схема аутентификации — используется вместо полноценного JWT/OAuth2 |

Код прочитан целиком (`app/main.py`, `app/crud.py`, `app/db.py`, `app/security.py`, `app/redis_client.py`, `app/schemas.py`, `app/config.py`, `docker-compose.yml`).

## 2. Data Flow Diagram (DFD)

DFD построена по уровню 0–1 с тремя доверенными границами (trust boundaries) в OWASP Threat Dragon (Diagram → STRIDE, 3 доверенные границы, 2 внешние сущности/хранилища, 1 процесс, 7 потоков данных). Полная диаграмма с привязанными угрозами и контрмерами экспортирована в **`threat-dragon-report.pdf`** (приложен к отчёту).

**Компоненты DFD:**
- **Внешняя сущность** — Пользователь (клиент/браузер)
- **Процесс** — Bank API (FastAPI): `/transfer`, `/transactions`
- **Хранилище данных** — PostgreSQL (`accounts`, `transactions`)
- **Хранилище данных** — Redis (кэш `tx:{user_id}:...`)

**Доверенные границы:**
- **TB-1 Public Internet** — между недоверенным клиентом и API
- **TB-2 DMZ / API-слой** — вокруг процесса Bank API
- **TB-3 Внутренний data-слой** — вокруг PostgreSQL и Redis (в `docker-compose.yml` порты 5432/6379 публикуются на `0.0.0.0` хоста, что фактически расширяет эту границу за пределы внутренней сети — отдельное архитектурное замечание)

**Потоки данных:**
1. User → API: `POST /transfer`, `GET /transactions` (заголовок `X-User-Id`)
2. API → User: JSON-ответ (статус перевода / список транзакций)
3. API → PostgreSQL: параметризованные SQL-запросы (`$1, $2…`)
4. PostgreSQL → API: результат запроса
5. API → Redis: `GET tx:{user_id}:{limit}:{search}` (чтение кэша)
6. Redis → API: cache hit / miss
7. API → Redis: `DEL tx:{user_id}` (инвалидация после перевода — **ключ не совпадает** с реальным форматом кэш-ключа, баг инвалидации)

## 3. Три наиболее критичные угрозы и контрмеры

Угрозы отобраны по модели **impact × attack surface × влияние на бизнес-процесс** (перевод денег — высокочувствительная транзакционная операция в банке).

### 3.1. Угроза №1 — Spoofing identity + IDOR / Broken Object Level Authorization (критичность: **Высокая**)

Проблема в цепочке `app/security.py` (`get_current_user_id`) → `app/crud.py` (`_must_own_account`) → эндпоинты `POST /transfer`, `GET /transactions`. Идентификатор пользователя полностью берётся из клиентского заголовка `X-User-Id`, без подписи, JWT или серверной сессии. Дальше вся авторизация («это ваш счёт?») сверяется с этим же неподтверждённым значением: и объект доступа, и субъект доступа по сути контролирует один и тот же недоверенный запрос.

**Обоснование критичности:**
- **Impact:** полная компрометация конфиденциальности (чтение чужой истории транзакций) и целостности (инициирование перевода с чужого счёта) — прямые финансовые потери клиентов и банка.
- **Поверхность атаки:** оба публичных эндпоинта (`/transfer`, `/transactions`), атака тривиальна — подмена одного HTTP-заголовка, без эксплойтов и спецнавыков (PoC: `curl -H "X-User-Id: 2" ...`).
- **Влияние на бизнес-процесс:** прямой удар по core-функции банка (перевод средств); репутационный и регуляторный риск (несанкционированный доступ к ПДн/финансовым данным).

**Контрмеры:**
| Тип | Контрмера | Что снижает | Уровень |
|---|---|---|---|
| Технический | Заменить `X-User-Id` на OAuth2/JWT с проверкой подписи, сроком жизни и серверной сессией | Spoofing identity | Код (`app/security.py`) |
| Технический | Централизованная проверка владения ресурсом (object-level authz) на каждом запросе на основе **подтверждённого** токена | IDOR / BOLA | Код (middleware/dependency) |
| Архитектурный | Вынести AuthN/AuthZ в отдельный доверенный слой (API Gateway / sidecar), не принимающий identity напрямую из запроса | Spoofing + IDOR | Инфраструктура |
| Процессный | Обязательный security-review (чек-лист OWASP API Security Top-10, BOLA) для каждого нового эндпоинта, работающего с object id | Повторное появление класса уязвимости | Процесс (SDLC) |

### 3.2. Угроза №2 — Race Condition (TOCTOU) при списании средств → double-spending (критичность: **Высокая**)

Два параллельных запроса на перевод с одного счёта могут пройти проверку баланса одновременно и списать сумму дважды — классический race condition. На пальцах это выглядит так:

1. Запрос A читает баланс счёта — допустим, 1000 ₽.
2. Почти в тот же момент запрос Б читает тот же баланс — тоже 1000 ₽.
3. Оба запроса проверяют «средств хватает?» и оба получают «да», потому что каждый смотрит на свою независимую копию старого значения.
4. Оба списывают деньги. По отдельности каждая проверка была верной, но итоговый баланс уходит в минус.

Технически это выглядит так (`app/crud.py`, функция `transfer()`, строки 22–33): баланс читается SELECT-ом без блокировки строки — `SELECT ... FOR UPDATE` не используется; проверка «хватает ли средств» выполняется уже в Python, после чтения; а сам `UPDATE` не содержит защитного условия `WHERE balance_cents >= $1`. При этом в схеме таблицы `accounts` (`app/db.py`) тоже нет `CHECK`-ограничения на `balance_cents`. То есть защиты от ухода в минус нет ни на одном уровне: ни в логике приложения, ни в самом SQL-запросе, ни в схеме БД.

**Обоснование критичности:**
- **Impact:** прямые финансовые потери (списание сверх реального баланса), нарушение инварианта «баланс не может уйти в минус» — критично именно для банковского домена.
- **Поверхность атаки:** требует лишь возможности отправить 2+ параллельных запроса на `/transfer` с одного счёта — доступно любому аутентифицированному (или, с учётом угрозы №1, любому) клиенту.
- **Влияние на бизнес-процесс:** прямое нарушение целостности основной транзакционной операции банка; потенциальный финансовый ущерб и расхождения в бухгалтерском учёте.

**Контрмеры:**
| Тип | Контрмера | Что снижает | Уровень |
|---|---|---|---|
| Технический | `SELECT ... FOR UPDATE` внутри транзакции либо атомарный `UPDATE ... WHERE balance_cents >= amount` с проверкой `rowcount` | Race condition / double-spend | Код (`crud.transfer`) |
| Технический | Idempotency-key для операции перевода (защита от повторной отправки клиентом/ретраев) | Дублирование транзакций | Код + API-контракт |
| Архитектурный | `SERIALIZABLE` isolation level с ретраями на конфликт сериализации для критичных денежных операций | Race condition | Инфраструктура (БД) |
| Процессный | Обязательные concurrency/race-тесты (нагрузочные параллельные сценарии) в CI перед релизом платёжной логики | Регресс по этому классу багов | Процесс (SDLC, QA) |

---

### 3.3. Угроза №3 — Security Misconfiguration: hardcoded-креды + расширенная поверхность data-слоя (критичность: **Средняя**)

Источник — `docker-compose.yml`: `POSTGRES_PASSWORD: postgres` прямо в коде, плюс порты 5432/6379 опубликованы на `0.0.0.0`. Пароль БД попадает в систему контроля версий вместе с остальным кодом. А публикация портов PostgreSQL и Redis на все интерфейсы хоста по факту расширяет доверенную границу TB-3 за пределы предполагаемой внутренней сети.

**Обоснование критичности:**
- **Impact:** при компрометации репозитория/хоста/образа — прямой доступ к БД с финансовыми данными в обход API и его (пусть и слабой) бизнес-логики.
- **Поверхность атаки:** ниже, чем у угроз №1–2 (требуется доступ к репозиторию, CI-артефактам или сетевому сегменту), однако при утечке учётных данных последствия могут быть масштабными. Поэтому угроза имеет средний приоритет, несмотря на высокий потенциальный ущерб.
- **Влияние на бизнес-процесс:** компрометация всей БД (а не отдельной транзакции) — потенциально массовый инцидент, а не точечный.

**Контрмеры:**
| Тип | Контрмера | Что снижает | Уровень |
|---|---|---|---|
| Технический | Секреты — через secret-manager (Vault/Cloud Secrets) или `.env`, исключённый из VCS и образов; ротация паролей | Hardcoded credentials | Код/конфигурация |
| Архитектурный | Не публиковать порты БД/Redis наружу хоста; доступ только из internal docker-сети (убрать `ports:` у `postgres`/`redis` в compose, оставить только для dev-профиля) | Расширение поверхности атаки data-слоя | Инфраструктура |
| Процессный | Secret-scanning в pre-commit/CI (например, тем же Semgrep `p/secrets` или `gitleaks`) как обязательный гейт перед мержем | Повторное появление секретов в репозитории | Процесс (SDLC, CI/CD) |

## 4. Процесс управления уязвимостями (SDLC)

### 4.1. SAST-сканирование (Semgrep)

Выполнен статический анализ исходного кода `app/` инструментом **Semgrep 1.186.0**.

**Шаг 1 — готовые правила.** Прогон публичных реестров: `p/security-audit`, `p/python`, `p/sql-injection`, `p/secrets`, `p/owasp-top-ten` (267 правил на 9 файлах) → **0 находок**. Это ожидаемый и валидный результат: все SQL-запросы в `asyncpg` параметризованы через `$1, $2…` (в т.ч. фильтр `search` в `list_transactions` — через `params.append(...)`, f-string используется только для номера плейсхолдера, не для пользовательских данных). **Классический SQL Injection в предоставленном коде не обнаружен.**

**Шаг 2 — кастомные правила.** Поскольку бизнес-логические и архитектурные проблемы (identity spoofing, race condition, hardcoded-креды) публичные реестры не ловят, написаны 3 кастомных правила (`custom-rules/bank-custom-rules.yaml`):
- `bank-unverified-identity-header` — доверие к `X-User-Id` без верификации (CWE-290/306)
- `bank-hardcoded-db-credentials` — захардкоженный пароль БД в YAML (CWE-798)
- `bank-transfer-missing-row-lock-race-condition` — списание баланса без блокировки строки (CWE-362)

Отдельно стоит отметить ограничение последнего правила: оно ищет буквальное текстовое совпадение конкретной пары `SELECT`/`UPDATE` из `crud.py` и не проверяет семантически, в одной ли транзакции выполняются запросы, действительно ли отсутствует `FOR UPDATE`, есть ли иная синхронизация или условие `WHERE balance_cents >= ...` — при любом изменении текста запроса правило просто перестанет матчиться, а не подтвердит/исключит проблему осознанно. Поэтому в правиле указан `confidence: MEDIUM`.

Прогон кастомных + публичных правил → **3 находки** (файл `semgrep-results.json`).

**Шаг 3 — ручное добавление IDOR.** В данном случае IDOR не был обнаружен использованными правилами SAST: для подтверждения уязвимости потребовался анализ бизнес-логики и сценария эксплуатации. Добавлена вручную в тот же JSON отдельной записью `manual-review.bank-idor-cross-account-transfer-and-read`, с явными полями `metadata.source = "manual-security-review"`, `validation_state = "CONFIRMED_MANUAL"` и PoC (`curl` с подменой `X-User-Id`), чтобы отличать её от автоматических находок SAST.

**Итог SAST:** 4 задокументированные находки в `semgrep-results.json` (3 автоматические + 1 ручная), формат — JSON на основе нативного вывода `semgrep --json` (с одной вручную добавленной записью, не являющейся результатом работы инструмента).

| # | check_id | Файл | Источник | CWE |
|---|---|---|---|---|
| 1 | `custom-rules.bank-unverified-identity-header` | `app/security.py` | Semgrep (custom rule) | CWE-290/306 |
| 2 | `custom-rules.bank-hardcoded-db-credentials` | `docker-compose.yml` | Semgrep (custom rule) | CWE-798 |
| 3 | `custom-rules.bank-transfer-missing-row-lock-race-condition` | `app/crud.py` | Semgrep (custom rule) | CWE-362 |
| 4 | `manual-review.bank-idor-cross-account-transfer-and-read` | `app/main.py` | Ручной security-review | CWE-639/284 |

### 4.2. Процесс выявления и обработки уязвимостей на уровне SDLC

Ниже — какие проверки безопасности должны стоять на каждом этапе разработки (Design → Code → Build/CI → Test/Staging → Release/Prod), чтобы находки, подобные описанным выше, ловились до прода, а не после инцидента.

**Ключевые элементы процесса:**
1. **Threat Modeling на этапе Design** — до написания кода: DFD + STRIDE (как в этом отчёте), результат — список угроз с приоритетом, трекается как бэклог security-задач.
2. **SAST в CI как обязательный гейт** — Semgrep с комбинацией публичных (`p/security-audit`, `p/owasp-top-ten`, `p/secrets`) и кастомных правил под специфику домена (банкинг: race conditions в денежных операциях, identity-проверки); блокировка мержа при находках severity ERROR/High.
3. **SCA (Software Composition Analysis)** — отдельно от SAST, проверка зависимостей (`requirements.txt`) на известные CVE.
4. **Secret-scanning** — отдельный гейт (pre-commit + CI), т.к. секреты утекают чаще всего через конфиги, а не через код приложения (как и показал наш пример с `docker-compose.yml`).
5. **Ручной security-review / пентест для бизнес-логики** — IDOR, race conditions и broken authorization не всегда выявляются SAST-инструментами автоматически. В нашем случае автоматическое сканирование не обнаружило IDOR и SQLi: IDOR был подтверждён вручную, а SQLi не воспроизвёлся при анализе предоставленного кода.
6. **Приоритизация и SLA** — найденные уязвимости классифицируются по severity (используя CVSS/бизнес-impact), для Critical/High в платёжной логике — ускоренный цикл фикса и ретеста перед допуском в прод.
7. **Регрессия** — после фикса каждая находка покрывается тестом (unit/integration), чтобы исключить повторное появление (особенно важно для race condition — нужен concurrency-тест, а не просто unit-тест).
8. **Обратная связь в Threat Model** — после инцидента/находки модель угроз (Threat Dragon файл) обновляется, чтобы не терять знания между итерациями разработки.
